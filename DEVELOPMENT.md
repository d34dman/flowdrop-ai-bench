# Development

How the repository is laid out, how the site is built, and where things go. For
contributing runs see [CONTRIBUTING.md](CONTRIBUTING.md); for the runner site see
[runner/README.md](runner/README.md).

## Layout

| Path | What |
|---|---|
| `corpus/v1/` | The three pages we wrote and host (`small.html`, `medium.html`, `large.html`), their gold Markdown bodies, and `manifest.json` with every target, protected name and homonym trap by position. Served at <https://d34dman.github.io/flowdrop-ai-bench/corpus/v1/>. Edited in place until the 1.0 tag; after that a change is `v2/`. |
| `corpus/build.py` | Regenerates the HTML, gold and manifest from `corpus/v1/src/`. Standard library only. |
| `prompt/redact.v1.md` | The one system prompt every model-calling cell runs with. Front-matter defines the glyph and the competitor list. `critic.v2.md` is the reviewer prompt for the Reflexion cell (v1 lacked the never-redact-the-subject rule). |
| `runs/`, `outputs/` | The dataset: one JSON (ledger + metering) and one Markdown output per run. The unit of contribution. Append-only; CI enforces it. |
| `exclusions/` | One JSON per run withdrawn from grading, with kind and reason. The run stays in `runs/`. See [CONTRIBUTING.md](CONTRIBUTING.md#excluding-a-run). |
| `traces/` | One gzipped JSON per run with the full FlowDrop execution: pipelines, jobs, checkpoints, sessions, metering. `python3 scoring/trace.py <run_id>` prints a timeline. |
| `scoring/score.py` | Deterministic scorer. `--explain <run_id>` shows its reasoning. |
| `data/` | `runs.csv` and `scores.csv`, generated by the scorer, published with the site. Not committed. |
| `site/` | The published site. See below. |
| `bin/` | `setup.sh` installs the runner site; `run_cell.sh` is a positional wrapper around `bench:run`. Run from the repo root. |
| `runner/` | The Drupal 11 site that runs the cells: the workflows as config and the `bench:*` Drush commands. |
| `.github/workflows/pages.yml` | CI: guards the dataset, scores it, builds one job per visual, assembles and deploys. |

## Build the site locally

```sh
python3 scoring/score.py && python3 site/build.py
cd _site && python3 -m http.server 8000
```

Open <http://localhost:8000/>. The pages fetch `data/scores.json`, so they need a server,
not `file://`. Standard library only, no Node.

`site/build.py` has stages that CI runs as separate jobs: `data` (scores, facets, shared
assets, corpus, outputs), `visual <id>` (one folder), `index` (the homepage), `list` (the
registry as JSON for the CI matrix). No argument runs them all.

## The site framework

Everything is defined once and read from two places.

- **`site/filters.json`** defines every filter: id, label, the `scores.csv` column, optional
  value order, label map and split character. Python builds `data/facets.json` from it; the
  browser draws the filter bar from it.
- **`site/registry.json`** lists the visuals in order. The homepage cards, the nav and the
  CI matrix come from this list.
- **`site/lib/framework.py`** loads rows, builds facets, and wraps a page in the site chrome
  through `ctx.page(...)`.
- **`site/lib/bench.js`** is the browser runtime: filter state in the URL query string,
  the filter bar, `Bench.ready(...)` for visuals, `Bench.pager(...)` for long lists, and
  helpers. Filter state is carried to every link marked `data-nav`, so a view is shareable
  by copying the address.
- **`site/lib/compare.js`** renders the two focus pages from one dimension.
- **`site/lib/bench.css`** is the one stylesheet.

A visual is a folder `site/visuals/<id>/` holding:

```
visual.json   {"title", "blurb", "filters": [ids from filters.json], "focus": optional filter id}
build.py      def build(ctx): writes ctx.out/index.html via ctx.page(...)
page.js       optional; runs Bench.ready(({rows, all, facets, state, focus}) => ...)
```

`rows` is the scored data after the active filters, `all` before them. The callback runs
on load and after every filter change. A visual with `focus` gets that filter as a single
select and `focus.value` is the chosen value. Adding a visual is a folder and a registry
line; the CI matrix picks it up. The step by step is in
[CONTRIBUTING.md](CONTRIBUTING.md#add-a-visual).

## Visuals

| Visual | Shows |
|---|---|
| `scorecard/` | Outcome per cell (variant × model × page) and every run with axes, output and trace. |
| `matrix/` | Variants × models, correct over graded per cell. |
| `cost/` | Cost against time per cell, and bar figures for $ per run, seconds per run, $ per correct run. |
| `by-model/` | One model, compared across the benchmarks. |
| `by-benchmark/` | One benchmark, compared across the models that ran it. |
| `traces/` | Index of captured traces, one page per trace. |
| `task/` | Corpus pages, traps, protected names, prompt. |

Filters: task, benchmark, model, page, outcome, tag, corpus. A filter a page does not show
still applies and the bar says so.

## Conventions

- Runs are never edited or deleted; a run that should not count is excluded.
- Corpus and prompt are versioned by folder and by hash in every run ledger.
- Filters and visuals are declared in JSON, never hard-coded in a page.
- Charts use text tokens for text and validated categorical colours for series. A model's
  colour is pinned in `site/palette.json` and never changes: adding a model means appending
  it there with the next free slot, so nobody else is repainted. No slot is red or near red;
  red belongs to the silent-failure outcome.
